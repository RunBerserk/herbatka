# Herbatka v1.0 — definition of done

This document is the **canonical scope and acceptance bar** for declaring **feature-complete v1.0**: a **single broker process** on **one deployment**, as robust as is reasonable there (persistence, recovery, external TCP contract), without multi-node high availability.

Last updated: 2026-05-12

## Alignment with roadmap

Per [roadmap.md — Declare Feature-Complete v1](roadmap.md), v1 complete means:

- Core broker **produce**, **fetch**, **persistence**, and **recovery** are stable for that single-node deployment.
- **Basic operability** and **automated tests** are in place (see [Verification](#verification) below).
- **Known critical risks** are either **resolved** or **explicitly accepted** (see [Open decisions and accepted risks](#open-decisions-and-accepted-risks)).

After v1, avoid scope creep in the v1 line; new capabilities belong in a v2 backlog ([roadmap.md](roadmap.md)).

## Verification

Source of truth for CI is [.github/workflows/ci.yml](../../.github/workflows/ci.yml). A v1 release candidate should pass the same steps locally (or on CI):

- `cargo fmt --all --check`
- `cargo clippy --all-targets -- -D warnings`
- `RUSTDOCFLAGS=-D warnings cargo doc --no-deps`
- `cargo test` (workspace-wide)

**Optional manual smoke** (not duplicated in CI commands above):

- Simulator + broker flow: [test-harness.md](../reference/test-harness.md)
- TCP server integration coverage: [tcp_server_smoke.rs](../../crates/herbatka/tests/tcp_server_smoke.rs)

## Single-node operations and continuity

What v1 **does** imply operationally:

- **One running broker** at a time against a given **data directory**; that directory is the durability boundary for segments and sidecars.
- **Continuity** after failure is primarily **restart** the same process (or process manager), and **restore** from operator backups if storage is lost—the product does not provide automatic handoff to another live broker.
- **Throughput under concurrent clients** may be limited by a shared in-process lock; see [status.md — Known Gaps / Risks](status.md) and v1 risk decision there.

This is **not** a “cluster failover story” (no coordinated second writer, no product-defined RTO across nodes).

## Explicitly not in v1.0

Release-scoped exclusions (clustering and HA). v1.0 does **not** include:

- Multi-node or **clustered broker** topology
- **Leader election**, **quorum**, or **consensus between brokers**
- **Split-brain handling** across multiple brokers
- **Automatic HA failover** between live broker instances (hot standby, controlled promotion)

Broader product backlog items that are also **out of v1.0** (protocol and UX) are tracked under [status.md — Later (TODO, not now)](status.md) — e.g. Protobuf on the wire, QUIC — to avoid duplicating that list here.

## Open decisions and accepted risks

Declaring v1 done requires each item to be either **implemented** or **documented as accepted** for v1:

| Topic | Pointer |
|-------|---------|
| Global `Mutex` / concurrent TCP clients | [status.md — Known Gaps / Risks](status.md); optional benchmark or explicit acceptance note |
| `Message.timestamp`: `SystemTime` in memory vs `u64` epoch ms on disk | **Resolved (2026-05-12):** `Message.timestamp` is `u64` epoch ms; [`now_epoch_millis`](../../crates/herbatka/src/time.rs); details in [roadmap.md](roadmap.md). |

Record the outcome in this file, in [status.md](status.md), or in the linked doc—**one** canonical sentence is enough per item.
